The persistant database storage will be in a different format
from the in-memory layout. The autocoder will generate the transformation between them.

Requirements:

1. Persistent parameter storage is mostly robust to bit flips
   One invalid parameter will not invalidate another valid parameter

2. A valid or partially valid persistant storage may be overlayed with another
   valid or partially valid persistant storage for redundancy

Assumptions:

1. All parameter datatypes are fixed-size

## Persistent storage

The persistant storage will hold fixed 12-byte records.
A record will have:

1. 2-byte ID. This could be CRC of prm name or something else.
2. 2-byte CRC16 (CCITT). CRC of value
3. 8-byte value. Could hold the entire parameter or partial. Smaller parameters will not use the additional bytes.

For parameters larger than 8-bytes, they will be split across multiple records.


## In-memory storage

The in-memory store needs to be space efficient and robust.
The in-memory store only needs to hold the validity state of a parameter.
The validity state of parameters will be held in "validity stores" (maybe come up with a good name?).
Because every parameter can be in one or more records, we can allocate a single bit for each mapped record in the validity store.
Every parameter will have a validity "mask" which can be used to validate the state of the parameter in memory.

For instance:

[32-bit validity mask][prm 1 value][prm 2 value][prm 3 value][etc.....]

Each parameter 1, 2, 3, etc will have a certain mask on the initial 32-bit validity mask.
We can create as many groups as needed for these parameters. All the masks can be stored
in the front of the in-memory buffer for alignment reasons.

## Conversion

### LOAD

To load parameters from the persistent store into the in-memory store we follow this procedure:

1. Receive memory (read from FRAM) which is a multiple of 12 bytes
2. Clear all the validity masks (if we are loading a fresh DB)
3. For each 12-byte chunk (parameter record):
   a. Validate the CRC16 against the value
   b. Look up the ID to get the parameter record validity mask
   c. memcpy the value into the proper offset in in-memory store
   d. Update the validity mask for this record to reflect that this segment of the parameter is valid

To allow loading one store onto a partially valid store, we should set of VALID-VALID precedence.
Otherwise the new store (if valid) should overwrite an INVALID segment.

PRM LOAD should never fail. It may _partially_ fail (we should report in telemetry the number of valid/invalid records)
During bootup, we can LOAD PRIME and LOAD BACKUP with different precendence so that the backup loads over invalid records of the PRIME

### STORE

Instead of computing the CRC8 on each PRM save. A PRM SAVE will simply save the value and set the
validity mask of the entire parameter to fully valid.

So each PRM SAVE will follow this procedure:

1. Overwrite the value of the in-memory record.
2. Set all parameter validity bits for this parameter to `1`.

Then during a DB save, we will:

1. Ask for a buffer from the buffer manager
1. Compute the largest multiple of 12 that fits in the buffer
1. Compute the number of persist transactions needed to complete the save
1. For each parameter in the DB:
  1. Make sure all validity bits are on
  1. For each record allocated for the parameter:
    1. Create a new record in the current persist transaction
    1. Copy proper chunk of the in-memory store into the persist record
    1. Copy compute the CRC16 of the chunk
    1. Populate the 2-byte ID in the persist record
1. Send each persist transaction down-stream to PrmStorage.
